# Bootstrap and maintain an agent environment

Current version: **0.10.2**. Read `references/recipes.md` for candidate toolchain commands, `references/contract.md` for the installed contract, `references/runtime.md` for failure receipts, targeted commands, task ingestion and default local change checks, and `references/assessment.md` for the required assessment output. Use `references/evaluation-loop.md` to test skill/AGENTS changes on fresh agent trials, `references/grading.md` to grade paired results, and `references/evaluation.md` for past trials; use `references/infrastructure.md` when Docker/Compose/Kubernetes/Helm files exist and `references/sandbox.md` for sandbox constraints. The repository's actual commands and requirements take precedence over these examples. Choose the tools, component boundaries, runner and checks from evidence; the registry and recipes are starting points. Preserve the invariant that unavailable checks fail visibly and that a later agent can reproduce the chosen workflow from the repo.

## Bootstrap scope

Treat a bootstrap-only request as authorization to configure the agent environment **within the specified repository roots**. Inspect broadly, but write only the scaffold and project configuration needed to operate it: `.agents/`, provider adapters, AGENTS.md/CLAUDE.md, command wrappers, ignored local cache settings, existing task/CI configuration, and relevant documentation. Edit project manifests, lockfiles or build/deployment configuration only when a specific setup or validation need justifies the change; record the reason and diff. Preserve existing user edits. Do not modify application source or tests merely to make validation pass, add placeholder tests, perform unrelated refactors, or write to sibling repositories unless they were included in the requested workspace. Report product defects as gaps; fix them when the user has also requested code changes.

Run only tools needed to inspect, install the declared project dependencies, configure the scaffold, and check its behavior. Inspect project scripts and transitive tool effects before running them; use non-mutating check modes for lint/format when available. A task runner may start other executables, so a literal executable allowlist in this skill would block valid checks without enforcing process isolation. Do not run unrelated programs or external deployments. Record consequential commands and unexpected side effects. Agent instructions define intent; actual file/process/network restrictions must come from the host agent's sandbox and approval settings (see `references/sandbox.md`).

## Assess and install

1. Inspect Git status, existing AGENTS.md/CLAUDE.md, CI, lockfiles, scripts, tests, build tools, container definitions, and deployment paths. Inspect root and nested packages. Ask for missing deployment targets or credentials only when needed for the actual deployment.
2. Inspect project roots recursively, including `backend/`, `frontend/`, nested workspaces, independent Git repos, Dockerfiles, Compose, charts and deployment manifests; the detector searches only common locations. For an install or redeploy, write `.agents/assessment.md` following `references/assessment.md`: record evidence, selected tools and capabilities relevant to this project, validation coverage, gaps, execution results and sandbox constraints. For `assess` alone, return the assessment without modifying the target. Run `python PATH_TO_THIS_SKILL/scripts/bootstrap.py assess TARGET` when Python is available (or `python -m agent_env assess TARGET` from this source checkout). Its detections are **proposals**, not proof. Investigate gaps and additional languages, packages, services, and tool-specific config; amend the proposals. If none are detected, install the common environment and implement a local component adapter.
3. For an install request, run `python PATH_TO_THIS_SKILL/scripts/bootstrap.py install TARGET` (or the source-checkout CLI). It deploys registered skills and agent definitions, creates a version record and commands registry, installs Bash/PowerShell wrappers, and sets an ignored local cache root. The installer preserves existing commands, so inspect and fix unsuitable candidates in `.agents/commands.json` before executing them.
4. Extend the target's registry, scripts, docs, skills, and CI based on observed behavior. Treat `.agents/commands.json` as the central run registry; add named commands for newly observed project tasks and declare their working directory, local environment setup, and sandbox needs when useful. Sandbox metadata is guidance for the coding agent, not permission or automatic elevation. Use `catalog --json` to inspect registered commands and existing `.vscode/tasks.json` tasks, then `lookup --component NAME --for-command COMMAND` to view a specific run before execution; use simple process tasks directly when appropriate, and adapt shell, dynamic or dependent tasks explicitly before running them. Give project-specific checks, such as one-file or one-test selection, named commands with declared parameters rather than inventing opaque flags. Use the installed `.agents/skills/bootstrap-agent-env/scripts/bootstrap.py` for later local reassessment; use a newer registry checkout to upgrade. Prefer a suitable existing repo-native task runner when the bundled Python runner adds an unnecessary dependency; document equivalent entry points.
5. Create components for distinct repository sections with separately operated build, test, runtime or release contracts, such as a UI and an API. Keep a complex application together when its internal modules share one validation contract; do not create a component for every package, module, or directory. The detector lists candidate folders, and the agent consolidates or extends them after inspecting the workspace. Map dependencies and determine the smallest reliable validation scope, falling back to a broader suite when the dependency graph is uncertain. A developer space containing separate repos may use `assets/scripts/workspace.py` with an explicit manifest; each repo retains its own runner and version record.
6. Build a capability inventory for each relevant component: setup, tests, static analysis, build, documentation, runtime checks, release validation and project-specific tasks. For each selected capability, record the evidence, exact native command, prerequisites, what a passing result proves, and any remaining gap. Select checks from observed requirements and existing tests/artifacts; do not add a check, package manager or new tool simply to fill a template. Syntax/config checks do not prove application behavior. If the project ships a runtime service, inspect its tests and release contract to decide whether a startup, request or integration check is warranted; record the missing runtime coverage if unavailable. Keep unrelated capabilities unconfigured or not applicable with a reason.
7. Before broad validation, inspect registered commands for implicit dependency resolution, package scripts, destructive effects and offline constraints. Run help, doctor, selected checks, and the broadest meaningful `validate` with real failures and successful paths. On failure, inspect actual output with `failures` and its metadata with `status`; keep persistent defects and fixes in tracked assessment or issue records. Add CI using the same registry; provision required toolchains and project dependencies there. For a checked-in lockfile, include the project-specific locked bootstrap step before CI validation or document evidence that installation is unnecessary. Use the broad Git-visible metadata fingerprint as the local default. Narrow inputs for a component only after verifying shared inputs and tool configuration are covered; force a run when inputs cannot capture a dependency. Always run full validation in CI. Do not mark unavailable tools, zero tests, cached skips or placeholder tasks successful coverage. Record changes and verification in `.agents/assessment.md`.
8. Only after meaningful local validation of every configured component, including release artifacts that the project actually ships, run `python PATH_TO_THIS_SKILL/scripts/bootstrap.py finalize TARGET` or the source-checkout CLI to record the applied skill version. Record unrun hosted CI separately; it does not by itself block finalization when equivalent local checks passed and no required bootstrap dependency is missing. Likewise, a declared install command with no required external dependencies need not be run solely to satisfy a template. If required validation cannot complete, keep a pending version and report it.

Read `../../registry.json` from the source checkout to see available skills and agent definitions; use `python -m agent_env registry plan TARGET` and `python -m agent_env registry install TARGET` to deploy defaults, or repeat `--select ITEM` to choose specific entries. Add new skills and agent definitions there with their source paths, versions, and destinations. The generated `.agents/registry-deployment.json` records file hashes for safe updates. Any valid child directory of `.agents/skills/` containing `SKILL.md` deploys by default even without a manifest entry. Any agent definition or associated file under `.agents/agents/<provider>/` also deploys by default (`claude` to `.claude/agents/`, `copilot` to `.github/agents/`, other providers to `.agents/agents/<provider>/`). Explicit manifest entries add versions, alternate source paths, destinations, and default selection. This allows future skills and agents to be added by folder alone. For a bootstrapped repository, use `python .agents/skills/bootstrap-agent-env/scripts/registry.py plan|install TARGET` to deploy newly added local skills and agents; its installed manifest and definitions are retained. For a reusable personal installation, run `python -m agent_env home plan` then `python -m agent_env home sync` from a source checkout. The latter stores the source under `~/.agents/agent-env` and exposes this skill in `~/.agents/skills`. If a destination differs from the last synced version, resolve the conflict rather than overwriting local changes. Use `--claude` to install a canonical skill copy into `~/.claude/skills` as well.

## Redeploy / upgrade

1. Read `.agents/bootstrap.json` and compare `applied_version` with this skill's current version. Review the installed code, current repo, selected tools, local extensions, CI, and Git diff; do not overwrite repo edits from upstream templates.
2. Review the deployed registry and runtime receipts and any locally edited skills or agents. Run assessment again; add relevant new recipes, resolve stale mappings, improve local workflow skills, and update cross-platform scripts as needed. The installer upgrades an unchanged managed runtime; an older runtime without a receipt or a locally edited runtime is preserved and must be reconciled deliberately for new `failures`, `status`, `catalog`, parameter and change commands. Record changes as pending, verify, then finalize.
3. If Docker, Compose, Kubernetes or Helm artifacts are part of the build/release path, register their non-deploy validation separately from application tests, provision the needed tools in CI, and report whether those checks actually ran. A passing app suite alone cannot validate a Dockerfile or manifest. Keep the installed registry authoritative for this repo. A version mismatch calls for review, not automatic regeneration. Refuse to mutate an unknown newer schema; explain the needed migration.

## Operations

- `assess`: read-only report with evidence, detected/unconfigured capabilities and opportunities.
- `install`: write and adapt the target repo; no deploy action.
- `validate`: execute only registered deterministic commands and propagate failures.
- `deploy-plan`: show artifact, target, credentials prerequisite, smoke check, and rollback path.
- `deploy`: only after an explicit request and project-specific target configuration. Verify built artifact identity and health. Never infer a production target from a generic template.

## Improve the instructions

For a change to this skill, a bundled agent definition, or the repository's AGENTS guidance, run `scripts/evaluations/loop.py` against relevant clean fixtures. Compare a baseline and changed source with the same model, runner settings and environment; capture raw traces, actual check logs, and structural grades. Have a separate reviewer score each case using `references/grading.md`, then compare matched repeats with `compare-scores`. Inspect new critical failures even when the average score rises. Add a fixture or assertion for a reproduced failure, then revise the smallest responsible instruction or resource. Keep live agent evaluations distinct from deterministic fixture tests: the latter cannot demonstrate that an agent read a skill or ran meaningful commands. Follow `references/evaluation-loop.md` for the runnable protocol and limitations.

Use the target's recorded `.local/` (or chosen alternative) for disposable cache where the sandbox requires a writable location; preserve preexisting tracked `.local` contents and compatible user overrides. See `references/sandbox.md` for diagnostics and tool-specific tradeoffs. Do not store secrets in cache. Claude Code uses a `.claude/skills` adapter to discover canonical `.agents/skills` skills. Registry deployment includes `.claude/agents` and `.github/agents` provider definitions. If CLAUDE.md masks AGENTS.md, import the latter with `@AGENTS.md` rather than duplicating it.
