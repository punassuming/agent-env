# Containers and deployment manifests

Treat build artifacts, declarative manifests, and a live deployment as separate capabilities. Enable a check only when the tool and project inputs exist; preserve evidence when unavailable. A Dockerfile, Compose file, Kubernetes manifest or Helm chart is evidence of a *possible* deliverable, not authorization to deploy or proof that the configuration works. Ask which files are actually used in release and which image/cluster/environment is the intended target.

| Evidence | Local or CI validation candidate | What it does **not** prove |
| --- | --- | --- |
| Dockerfile or Containerfile | `docker buildx build --check -f FILE CONTEXT` where supported; then a real `docker build` (or project's existing builder), verify the resulting image and run a smoke check if practical. | Build checks do not produce an image, and a successful image build is not deployment verification. Compare Dockerfile context, lockfiles and runtime entrypoint. |
| Compose file | `docker compose -f FILE config --quiet`, followed by service startup and health/integration checks where CI has Docker and dependencies. | Parsing is not proof that images build, services become healthy, or secrets are available. |
| Raw Kubernetes YAML | Validate syntax/schema with an appropriate tool and cluster API version; use `kubectl apply --dry-run=client -f PATH` only after confirming its client-side behavior in this environment. For admission/schema checks, `--dry-run=server` needs access to the intended cluster. | Client validation is not a rollout, and even server dry-run does not persist the resource. Distinguish image tag substitution and environment overlays. |
| Helm chart | `helm lint CHART`, `helm template RELEASE CHART -f VALUES` for each relevant environment/variant; validate rendered manifests where possible. | Lint/template do not verify CRDs, admissions, deployed image availability, or live readiness. |

Keep artifact identity explicit: tag/digest, target registry, namespace/environment, secrets and authentication source, health check and rollback path. Register read-only `deploy-plan` separately from `deploy`; never put `deploy` in `validate`. For a project that ships an image or manifest, add its non-deploy validation to the repository and CI, or record why it cannot run and leave its coverage pending. A passing application unit suite alone does not validate its existing release artifacts. Avoid forcing Docker/Kubernetes/Helm on a repo where those files are documentation or unused examples.

CI provisioning belongs with the corresponding validation command. A laptop without Docker or kubectl may still run source checks locally, while CI validates images and manifests; report these as separate results and do not claim CI passed before a run. Running `helm template` or Docker build may invoke plugins, fetch images or dependencies, or execute build scripts: inspect project code and network policy before probing an unfamiliar target. A rendered manifest with an unresolved placeholder image is not deployable.

Official references: [Docker build checks](https://docs.docker.com/build/checks/), [Docker Compose config](https://docs.docker.com/reference/cli/docker/compose/config/), [kubectl apply](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_apply/), [Helm lint](https://helm.sh/docs/helm/helm_lint/), [Helm template](https://helm.sh/docs/helm/helm_template/).
