# Candidate recipes

Use detection as a hypothesis. Read the project's configuration before registering a command; run a harmless probe when possible. Do not invent project scripts or assume optional tools are installed.

| Evidence | Install/bootstrap | Validate candidates | Notes |
| --- | --- | --- | --- |
| `Cargo.toml` | `cargo fetch --locked` if appropriate | `cargo fmt --all -- --check`; `cargo clippy --all-targets -- -D warnings`; `cargo test`; `cargo build` | rustfmt and clippy are optional rustup components. |
| `go.mod` or `go.work` | `go mod download` where applicable | `gofmt` difference check; `go vet ./...`; `go test ./...`; `go build ./...` | Determine workspace and module scope. |
| `pyproject.toml` + `uv.lock` | `uv sync --locked` | `uv run --locked pytest`, Ruff only if declared | Workspace members can inherit a root lockfile and bootstrap. Use `UV_CACHE_DIR`; tests may be elsewhere. |
| Python without uv | existing install mechanism | existing test/lint/typecheck commands | Never switch package manager silently. |
| `package.json` + `package-lock.json` | `npm ci` | actual scripts from package.json | Reject placeholder test scripts. |
| `package.json` + `pnpm-lock.yaml` | `pnpm install --frozen-lockfile` | actual scripts from package.json | Members inherit the root lockfile and bootstrap once at the workspace root. |
| Gradle wrapper | wrapper | `check`, `build`, or project-specific tasks | On Windows invoke `gradlew.bat`; inspect wrapper and plugins. |
| Android Gradle app | wrapper + Android SDK | module/variant `lint`, unit test and `assembleDebug` tasks | Identify modules, variants, SDK, and signing needs. |
| ASP.NET/C# project or solution | `dotnet restore` with declared SDK/feeds | `dotnet format --verify-no-changes`, `dotnet test`, `dotnet build` / `publish` for selected project or solution | Honor `global.json`, test runner, lock/restore behavior, target framework and feed auth; don't assume all test projects are referenced by a solution. |
| Django `manage.py` | declared Python installer | `python manage.py check`; tests through project's runner; migration check such as `makemigrations --check --dry-run` when applicable; lint/format only if configured | Distinguish DB-free checks, migration checks requiring DB access, tests, and production-only `check --deploy` with real settings. |
| Angular workspace (`angular.json`) | declared Node package manager, from the Angular project root | existing `ng test --watch=false` target and `ng build`; configured lint or type checks | Inspect each project's `architect` targets, test builder and browser requirements. An Angular CLI installation alone does not imply a test target or working headless browser. |
| Express API | declared Node package manager | actual API package `test`, `lint` and `build` scripts; route/integration tests when present | Express is a library; use the project's own runner and server entry point. Parsing `server.mjs` proves syntax only. |
| Sails API | declared Node package manager | existing test script and integration checks that lift the app when necessary | A test of `config/routes.js` alone proves only route mapping, not a running controller or datastore. Inspect adapter and database needs. |
| React Router frontend | declared Node package manager | existing frontend tests and build; browser or route tests if provided | Identify declarative, data or framework mode from dependencies/configuration. Do not assume React Router CLI or scripts in declarative-mode Vite apps. |
| HTML / static site | project's native Node/Python setup, if needed | existing test, syntax, lint, accessibility/build or static generation commands | Inspect actual scripts and generated output; plain HTML may need no package manager. |
| Dockerfile / Compose / Kubernetes YAML / Helm | provision only the required tools in CI | See `infrastructure.md` for distinct check, build, render and rollout candidates | Existing release artifacts warrant validation without inferring a deployment target. |

For a combined Django/Angular or Node API/React workspace, create independent component entries rooted at the real manifests. Choose a root aggregator only when a workspace manager or explicit project command warrants it; it must not hide missing backend checks. For sibling Git repositories, install a separate registry, CI and version receipt into each repository and coordinate only through an explicit workspace manifest. If dependencies, lockfiles or browsers are absent, record their exact effect and keep framework tests/builds pending; a passing parse check is narrower coverage. For additional tools, extend this catalog and the target's local registry. Prefer documented cache overrides under `.local/cache` only if confinement is needed. `GRADLE_USER_HOME` holds config and wrapper distributions as well as cache; changing it may change credentials and behavior. Keep environment setup consistent in Bash, PowerShell and CI via the repo runner; use tool-native configuration where that is more reliable.
