# Agent evaluation protocol and observed trials

Run independent coding agents on unfamiliar, disposable workspaces. Give each agent the skill path, target path, bootstrap request and a complete description of the environment it sees. Capture actual tool versions and paths, available SDKs, dependency/cache state, project files, Git state, writable roots, and network policy. Identify which constraints are enforced by the operating system versus trial instructions. The generators in `scripts/evaluations/` create committed fixture repositories and a `run_manifest.json`; inspect the generated `EVAL_ENV.md` and correct environment details if the host differs. They do not provide process isolation: all subagents in this runtime share the host filesystem and network. A prohibition in a prompt is not a sandbox policy; inspect agent side effects, including implicit package downloads and global cache use. Never describe the trial as proof that network or filesystem access was blocked.

Inspect target files, Git diff, command output, cache side effects, CI configuration and the agent summary. Do not substitute a detector unit test for agent behavior. Check against `assessment.md`: tool selection has evidence; runnable validation matches real tests, lint, formatting, docs and build; release artifacts have separate coverage; missing tools or false-positive checks remain pending; CI provisions tools and invokes the same commands; `.local` is ignored; skills and provider definitions are installed; deployment requires a known target. Repeat after changing the skill if agents incorrectly declare coverage or hide failures. A CI file that has not executed is a proposal, never a passing check.

Create fresh runs (paths are ignored and must initially be empty):

```bash
python .agents/skills/bootstrap-agent-env/scripts/evaluations/prepare.py
python .agents/skills/bootstrap-agent-env/scripts/evaluations/prepare_web_cases.py
python .agents/skills/bootstrap-agent-env/scripts/evaluations/prepare_stack_cases.py
python .agents/skills/bootstrap-agent-env/scripts/evaluations/inspect.py --help
```

Use `--output PATH` for a new run. Start agents against different generated targets, include `EVAL_ENV.md` verbatim in each brief, and ask them to follow this skill. Compare the resulting registry and assessment to the original project evidence, then amend recipes and skill instructions before rerunning a previously failed case. Do not confuse scaffold creation with native compiler/SDK execution.

Four independent Luna trials in September 2026, using disposable fixtures under `.local/evals/`:

| Workspace | Observed agent behavior | Outcome / refinement |
| --- | --- | --- |
| Python/uv test-only service | Fixed malformed lockfile and project metadata, provisioned pytest and Ruff, wired CI, confirmed one collected test and all checks, finalized 0.3.0. | A valid, evidenced completion. |
| pnpm root plus UI package | Detected both packages and delegated install to root; discovered `node --test` returns success with zero tests and declared lint/build tools were missing. Narrowed validation and left version pending. | Require meaningful test coverage; probe advertised scripts instead of trusting successful exits. |
| Android flavored app | Saw Gradle wrappers only printed text; added static/docs checks and CI, but left actual build/test pending because SDK and genuine build were absent. | An echo-only wrapper is not a build or test; agent must select real variant tasks and SDK provisioning from evidence. |
| Separate Go and Rust repos | Gave each repo its own commands, skills, CI, cache and pending version; created a workspace coordinator. Missing local Go/Rust tools caused visible validation failures. | Make missing toolchains explicit; CI provisioning does not count as a local or remote pass. |

The trials identified a package-level gap too: the installed repository initially received skills and provider copies but not its own manifest and registry manager. The installer now retains both and can discover new child skill folders and provider definitions automatically. Reevaluate on new fixture types when recipes or provider adapters change.

## Targeted 0.4.0 retry

On a fresh static HTML/JS + Docker/Kubernetes fixture, a Luna agent ran one native test plus lint/build and left version **pending 0.4.0** because Docker and manifest checks could not run. Initially it still wrote CI covering application scripts only. After a follow-up to inspect the infrastructure guidance, it registered image build and manifest schema candidates in `validate`, added Docker provisioning in CI, and corrected `doctor` so the declared Docker prerequisite is visible. Local `validate` then failed at missing Docker with exit 127, while app checks passed; CI had not run. The registry used a pinned containerized schema checker, whose image would require a pull when first used. The placeholder deployment image still needs a real digest or tag before deployment. This retry shows better pending-state behavior and also shows why reviewers should inspect whether the generated CI actually covers every shipped artifact.

On a fresh FastAPI + pnpm/React fixture without a lockfile or `node_modules`, a Luna agent invoked `pnpm --filter @eval/ui lint`. The root declared pnpm 9.15.9 and the host launcher was pnpm 11.25.0. The invocation instead started an install across four workspaces, reused 137 cached packages (`downloaded 0`), generated `node_modules` and a lockfile, then exited on `ERR_PNPM_IGNORED_BUILDS` for esbuild. It also altered workspace YAML; the agent restored it and removed generated files. Static backend and UI syntax checks passed; `uv run --locked --no-sync pytest` exited 2 because pytest was absent, creating only an empty ignored virtual environment. The agent left version pending 0.4.0 and reported unverified integration tests. This does not establish whether the pnpm version mismatch caused the install, but demonstrates that a filter/lint argv can be unsafe to probe without inspecting the launcher, lockfile and cache. The skill now warns explicitly against this probe in offline trials.

## Evaluation-loop smoke run, version 0.5.0

The `scripts/evaluations/loop.py` harness prepared a fresh controlled Node app. An independent Luna agent bootstrapped it and finalized 0.5.0. Before attaching command evidence, the grader marked the finalized version premature because it had only filesystem artifacts. An operator then reran `doctor --json` and `validate --all` in the agent-produced target: both exited zero, with Node reporting **one passing test** plus lint and build success. `record` attached those receipts and an explicitly labeled **summary**, not a raw tool trace; the grader reported no structural issues for that case and kept hosted CI execution unverified. The other generated cases were unrun in this trial. This verifies the evaluation loop's recording and grading behavior for one agent-produced target, not reliability across models or an improvement over 0.4.0. Preserve full tool traces in future automated agent CLI runs where the provider supports them.
