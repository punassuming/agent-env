# Agent evaluation protocol and observed trials

Run independent coding agents on unfamiliar, disposable workspaces. Give each agent the skill path, target path, bootstrap request and a complete description of the environment it sees. Capture actual tool versions and paths, available SDKs, dependency/cache state, project files, Git state, writable roots, and network policy. Identify which constraints are enforced by the operating system versus trial instructions. The generators in `scripts/evaluations/` create committed fixture repositories and a `run_manifest.json`; inspect the generated `EVAL_ENV.md` and correct environment details if the host differs. They do not provide process isolation: all subagents in this runtime share the host filesystem and network. A prohibition in a prompt is not a sandbox policy; inspect agent side effects, including implicit package downloads and global cache use. Never describe the trial as proof that network or filesystem access was blocked.

Inspect target files, Git diff, command output, cache side effects, CI configuration and the agent summary. Do not substitute a detector unit test for agent behavior. Check against `assessment.md`: tool selection has evidence; runnable validation matches real tests, lint, formatting, docs and build; release artifacts have separate coverage; missing tools or false-positive checks remain pending; CI provisions tools and invokes the same commands; `.local` is ignored; skills and provider definitions are installed; deployment requires a known target. Repeat after changing the skill if agents incorrectly declare coverage or hide failures. A CI file that has not executed is a proposal, never a passing check.

Create fresh runs (paths are ignored and must initially be empty):

```bash
python .agents/skills/bootstrap-agent-env/scripts/evaluations/prepare.py
python .agents/skills/bootstrap-agent-env/scripts/evaluations/prepare_web_cases.py
python .agents/skills/bootstrap-agent-env/scripts/evaluations/prepare_stack_cases.py
python .agents/skills/bootstrap-agent-env/scripts/evaluations/prepare_framework_cases.py --output .local/frameworks-fresh
python .agents/skills/bootstrap-agent-env/scripts/evaluations/inspect.py --help
```

Use `--output PATH` for a new run. Start agents against different generated targets, include `EVAL_ENV.md` verbatim in each brief, and ask them to follow this skill. Compare the resulting registry and assessment to the original project evidence, then amend recipes and skill instructions before rerunning a previously failed case. Do not confuse scaffold creation with native compiler/SDK execution.

Four independent Luna trials in September 2026, using disposable fixtures under `.local/evals/`:

| Workspace | Observed agent behavior | Outcome / refinement |
| --- | --- | --- |
| Python/uv test-only service | Fixed malformed lockfile and project metadata, provisioned pytest and Ruff, wired CI, confirmed one collected test and all checks, finalized 0.3.0. | A valid, evidenced completion. |
| pnpm root plus UI package | Detected both packages and delegated install to root; discovered `node --test` returns success with zero tests and declared lint/build tools were missing. Narrowed validation and left version pending. | Require meaningful test coverage; probe advertised scripts instead of trusting successful exits. |
| Android flavored app | Saw Gradle wrappers only printed text; added static/docs checks and CI, but left actual build/test pending because SDK and genuine build were absent. | An echo-only wrapper is not a build or test; agent must select real variant tasks and SDK provisioning from evidence. |

The trials identified a package-level gap too: the installed repository initially received skills and provider copies but not its own manifest and registry manager. The installer now retains both and can discover new child skill folders and provider definitions automatically. Reevaluate on new fixture types when recipes or provider adapters change.

## Targeted 0.4.0 retry

On a fresh static HTML/JS + Docker/Kubernetes fixture, a Luna agent ran one native test plus lint/build and left version **pending 0.4.0** because Docker and manifest checks could not run. Initially it still wrote CI covering application scripts only. After a follow-up to inspect the infrastructure guidance, it registered image build and manifest schema candidates in `validate`, added Docker provisioning in CI, and corrected `doctor` so the declared Docker prerequisite is visible. Local `validate` then failed at missing Docker with exit 127, while app checks passed; CI had not run. The registry used a pinned containerized schema checker, whose image would require a pull when first used. The placeholder deployment image still needs a real digest or tag before deployment. This retry shows better pending-state behavior and also shows why reviewers should inspect whether the generated CI actually covers every shipped artifact.

On a fresh FastAPI + pnpm/React fixture without a lockfile or `node_modules`, a Luna agent invoked `pnpm --filter @eval/ui lint`. The root declared pnpm 9.15.9 and the host launcher was pnpm 11.25.0. The invocation instead started an install across four workspaces, reused 137 cached packages (`downloaded 0`), generated `node_modules` and a lockfile, then exited on `ERR_PNPM_IGNORED_BUILDS` for esbuild. It also altered workspace YAML; the agent restored it and removed generated files. Static backend and UI syntax checks passed; `uv run --locked --no-sync pytest` exited 2 because pytest was absent, creating only an empty ignored virtual environment. The agent left version pending 0.4.0 and reported unverified integration tests. This does not establish whether the pnpm version mismatch caused the install, but demonstrates that a filter/lint argv can be unsafe to probe without inspecting the launcher, lockfile and cache. The skill now warns explicitly against this probe in offline trials.

## Evaluation-loop smoke run, version 0.5.0

The `scripts/evaluations/loop.py` harness prepared a fresh controlled Node app. An independent Luna agent bootstrapped it and finalized 0.5.0. Before attaching command evidence, the grader marked the finalized version premature because it had only filesystem artifacts. An operator then reran `doctor --json` and `validate --all` in the agent-produced target: both exited zero, with Node reporting **one passing test** plus lint and build success. `record` attached those receipts and an explicitly labeled **summary**, not a raw tool trace; the grader reported no structural issues for that case and kept hosted CI execution unverified. The other generated cases were unrun in this trial. This verifies the evaluation loop's recording and grading behavior for one agent-produced target, not reliability across models or an improvement over 0.4.0. Preserve full tool traces in future automated agent CLI runs where the provider supports them.

## Paired Luna studies, September 2026

Two matched fixture pairs were prepared with identical committed `EVAL_ENV.md` addenda, the same `gpt-6-luna` agent, host and prompt wording apart from the source skill path. The baseline skill was frozen at commit `4bec35a` (0.5.0); the candidate was frozen at `2aea147` (0.6.0). The agent only received its target, skill and environment brief. After each agent finished, the operator independently reran registered commands, captured output logs and test counts, then reviewed diffs and assessments. Source content hashes matched the frozen worktrees. Grading was **unblinded**, the subagent interface exposed final summaries rather than raw tool traces, hosted CI did not run, and the requested no-fetch constraint was a prompt instruction rather than OS isolation.

| Fixture | 0.5.0 observed | 0.6.0 observed | Reviewed result |
| --- | --- | --- | --- |
| Mixed npm workspace + Python service | Agent found the detector-missed Python suite. Independent `validate --all`: two Node tests and one Python unittest passed; finalized. CI sets up Node/Python, runs `npm ci`, then validation. | Same three tests passed and finalized. CI sets up Node/Python and validates without `npm ci`; this fixture has no external Node dependencies, so its checks are currently runnable. | **100 → 100**. Both cover observed components and checks. If external dependencies are introduced, CI must use the lockfile. |
| Static HTML/JS + Dockerfile + Kubernetes manifest | Native lint, one test and build passed; Docker Buildx check and kubeconform schema check blocked locally; version pending. CI provisions tools but registers no real image build. | Same native checks passed and infrastructure remained blocked; version pending. CI registers a real Docker image build and delegates kubeconform through a Node adapter that uses a pinned container image. | **92.5 → 100** on the reviewed rubric. CI execution, image build and schema validation are still unverified. The adapter adds a container image pull and extra script to maintain. |

The first structural grade wrongly reported that the candidate lacked Kubernetes schema validation: it searched only registered argv and missed `scripts/check-manifest.js` calling kubeconform. A regression test now covers delegated local adapters. Regrading **both** variants with the corrected structural rule changed the static candidate from 82.5 to 100. The CI rating for the mixed candidate was also revised from 1 to 2 after inspecting its zero-dependency package manifests; requiring `npm ci` here would reward a command the current checks do not need. Preserve both original and corrected reports in the ignored trial directory when reproducing this analysis. The skill now asks agents to document when a checked-in lockfile does not require installation for their CI checks.

These are **one pair per fixture**, not five independent repeats. `compare-scores` returns `trace_incomplete` for both because only agent summaries were available. The score change measures the documented review judgment and structural evidence in these runs; it does not establish that 0.6.0 generally outperforms 0.5.0. Repeat with raw agent traces, provisioned CI, more cases and fresh runs before accepting a general improvement claim.

## Framework combination trials, September 2026

Three independent Luna agents used frozen 0.6.1 against new repository layouts. The Django/Angular agent overrode an empty nested-component detector, registered separate backend/frontend checks and CI, and left the version pending because neither Django nor Angular CLI was installed. The Express/React Router agent registered a *root-only* npm workspace aggregate; its CI used the registry, but a member could not be run by its own component name. Express, Vitest and Vite were absent; validation failed and the version remained pending. The Sails/React Router agent created separate repository environments and a workspace coordinator. Its Sails API `validate` passed a config-only route test and syntax checks **while the Sails dependency was absent**; a real lift/HTTP route check remained unverified. The web build/test failed on missing dependencies, leaving both versions pending. None of the generated CI workflows executed. The available subagent interface exposed summaries, not raw tool traces; independently review all target diffs and command outcomes before treating these as evidence of effectiveness.

The initial Django/Angular fixture declared Angular 19 with host Node 24. Angular's official version matrix excludes Node 24 for Angular 19, so that trial cannot establish whether its generated CI would work even after packages were installed. The fixture was corrected to Angular 20.2 with compatible TypeScript and must be regenerated for further comparisons. The observed Express root-only and Sails config-only gaps motivated 0.7.0's explicit member registry and service runtime guidance. Any 0.7.0 trial must use fresh fixtures, label missing dependencies separately from runtime success, and leave CI execution unverified until a hosted run exists.

Fresh 0.7.0 Luna trials used the same agent model, host, permission mode and prompt shape. On Express/React Router the agent registered separate root, API and web components, including an HTTP `/health` probe; API syntax passed and framework tests/build remained blocked on missing packages. On Sails/React Router each child repo retained independent CI and pending version; the API added a startup/HTTP smoke script to `validate` and CI, which fails locally without Sails even though the config-only test passes. On Django/Angular the agent again found both nested members and this time provisioned Chrome for the declared Karma test in CI. Angular 20.2 replaced Angular 19 in this fresh fixture, so its committed starting tree differs and is **not a matched version comparison**. All three CIs remain unexecuted. No trial installed packages or deployed. Review is based on final subagent summaries and filesystem/command inspection; raw tool traces were unavailable, so it cannot establish general agent success rates.

The first 0.7.0 structural grade incorrectly flagged the Express root `test`/`build` scripts as missing because the registered root `validate` delegates to `api` and `web` while the independently registered members each expose their matching scripts. The grader now recognizes only simple, exact npm workspace aggregations with each delegated member command present; a regression test checks both acceptance and a missing member build. With the corrected rule, the fresh Express target has no structural issues. This correction does **not** mean the missing Express/Vitest/Vite packages or hosted CI have been validated. The Sails case required human review: its original structural grade was clean even though its Sails runtime was never exercised. The added smoke check corrects the command coverage but remains blocked locally.
